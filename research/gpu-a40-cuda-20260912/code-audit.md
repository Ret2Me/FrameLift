# Rust decoder → GPU feasibility: read-only code audit

Audit date: 2026-09-12. Scope: current source, existing measurements, local device exposure. No decoder edits, compilation, hardware changes, GPU work or benchmark interruption were performed. This memo is implementation evidence and engineering inference, not a measured CUDA performance result or a novelty claim.

## Findings in one paragraph

The code has substantial independent work across recordings, windows, frontends, clock hypotheses, models and gains. Those batch axes are a better GPU opportunity than trying to parallelize every symbol of one four-state Viterbi recurrence. A narrow, independently qualified backend can retain CPU input verification, model preparation, checkpoint commits and received-CRC validation while batching interpolation, sequence detection and eventually integer bit processing on the GPU. However, the current numerical contract is primarily f64 with specified summation and tie order. Merely replacing it with FP32, cuFFT, Tensor Cores, parallel reductions or FMA does not establish losslessness. No CUDA device or toolkit is exposed here, so a real A40 throughput or zero-loss claim cannot currently be measured.

## Local device and software evidence

- `command -v nvidia-smi` and `command -v nvcc` returned no path; `/dev/nvidia*` returned no device. This means this environment does not expose a usable NVIDIA setup, not that the user owns no A40 elsewhere.
- No CUDA backend or CUDA crate is configured in `Cargo.toml`/`Cargo.lock`; source search found no implemented GPU path.
- Existing graphify graph has 7,287 nodes and primarily historic Python sources. Query expansion used exactly `[parallel, performance, decode, runtime, cache, benchmark, signal]`; its result did not answer the current Rust CUDA mapping. Direct Rust source was therefore authoritative. No graph rebuild was performed.

## Proposed minimum GPU experiment

1. Preserve the frozen CPU executable and its accepted complete result sets. Create a separate optional backend identity/session; never silently resume a CPU session under a changed numeric backend.
2. CPU initially performs audio conversion, source hashing, exact window preparation, timing ranking and channel/noise-model fitting. Upload each prepared frontend once per useful batch.
3. GPU interpolates a batch of already specified clocks and runs many independent four/eight/sixteen-state trellises. Keep the existing per-symbol sequence order, f64 operations, low-predecessor tie rule and full traceback. Pack output decisions as bits or bytes rather than returning f64 ±1 arrays.
4. CPU independently executes the existing full framing/CRC/UI validators and canonical output ordering. Record transfer, kernel and end-to-end times separately. The initial objective is equality plus useful overall acceleration, not extra recovered packets.
5. If CPU framing dominates after acceleration, add separately qualified integer NRZI/G3RUH/flag-candidate kernels. Return candidate bytes plus exact trial provenance, then independently revalidate FCS/UI on CPU.
6. Only after this baseline backend passes should a separate experimental FP32, approximate numerical path or larger hypothesis bank be tested. Its additional yield and any losses must be measured, not described as the same algorithm running faster by definition.

### Memory and transfer arithmetic (illustrative, not a measured allocation)

A 6 s interval at 9,600 symbols/s contains approximately 57,600 symbols before startup/guard removal. At 16 states, the current one-byte-per-predecessor traceback is about 921,600 bytes per trial. A thousand simultaneous trials therefore need about 0.92 GB of traceback alone, plus observations, outputs and staging buffers. Bounded length/state-count batches can fit this comfortably on a large accelerator, but creating every intermediate stream for an entire campaign at once is unnecessary. Each survivor has only two possible predecessors, so an exact one-bit survivor representation could reduce traceback storage eightfold if state reconstruction and packing are independently tested. This is a storage-layout change, not permission to shorten the traceback.

Returning 57,600 hard decisions as f64 costs about 460,800 bytes per trial; packed bits are about 7,200 bytes. Device-side packing or flag discovery can matter as much as the arithmetic kernel once processing is batched. These figures are upper-envelope arithmetic for the illustrative window, not profiler observations.

## Exactness requirements

- `rust/dsp.rs:3–7` explicitly documents f64 without fast-math or explicit fused multiply-add, and warns that even CPU library changes can differ by ulps. GPU FP64 alone does not make operation order, division, transcendental functions and contraction identical.
- `rust/sequence.rs:339–355` and `rust/innovation.rs:462–478` specify predecessor and final-state ties. Preserve all branches, deterministic label ordering and free endpoints.
- Keep existing validation order, finite/magnitude checks, limits and error handling. Silent underflow handling, device-buffer overflow, unsupported configurations and half-finished tasks must not become apparently complete zero-frame results.
- CUDA FMA contraction must be explicitly controlled for a strict backend; one must still test the resulting machine arithmetic. FFT library replacement and transcendental evaluation should initially stay outside the bit-exact claim.
- A parallel prefix/Viterbi semiring scheme is mathematically attractive, but changes operation association in floating point. It also does substantially more state-composition work than four-state serial ACS. Treat it as a second research branch rather than the obvious lossless first port.
- Comparing only packet counts is inadequate. Compare decisions, accepted frame bytes/FCS, windows, model identities and parameters, scores/order, rejection reasons and task completeness. Existing independent pre-optimization oracles are useful starting points: `rust/sequence.rs:680`, `rust/innovation.rs:502`, `rust/dsp.rs:1019`, and protocol differential tests.
- Returning CRC-passing candidates from an approximate GPU and rerunning only those on CPU does **not** prove no losses: a GPU false negative creates no candidate to recheck. A conservative fallback mechanism needs an actual numerical decision certificate or complete CPU replay, not a heuristic margin alone.

## Existing measured performance, and what it does not establish

`work/receiver-speed-20260912-v1/real-pairs/summary.json` contains four paired CPU runs on two already used recordings, both AB/BA orders, all deterministic comparisons equal:

- summed wall time: 2,199.859497038 → 1,186.931073010 s;
- speedup: 1.853401×, or 46.045142% less wall time;
- summed CPU time: 3,077.62 → 1,669.14 s.

This was CPU implementation/build/cache optimization on a shared VM, not an A40 test and not an isolated cache microbenchmark. The older `reports/lossless-receiver-speed-20260910.md` reports stage-level timing and identifies costly repeated bank preparation and unbuffered I/O; it also explicitly records unavailable `perf` access. I found no current kernel-level profiler evidence establishing what percentage of the optimized full pipeline is spent in Viterbi, interpolation, median ranking or protocol parsing. Therefore an end-to-end GPU speedup cannot responsibly be predicted as 10×/100× from source inspection.

## Algorithm-development opportunities exposed by the audit

1. **Soft-output sequence detection**: the current MLSE returns hard ±1 decisions, explicitly not calibrated LLRs (`rust/sequence.rs:263–265`). A separately validated max-log/BCJR or list-sequence branch could supply reliability for actual coded links. It must be matched to the transmitter's real FEC; adding an LDPC decoder cannot create coding gain in an uncoded AX.25 transmission. BCJR/list decoding and GPU execution are established method families, not novelty by themselves.
2. **Longer/time-varying channel model**: current channel transfer uses three fixed taps and nearby/disjoint anchor selection. A controlled longer-memory or time-varying channel/noise model could improve robustness at increased state cost, making batched GPU execution more valuable. Compare against the retained fixed three-tap branch with matched budgets and held-out recordings.
3. **PSK/FEC coverage before generic AI claims**: native PSK is opt-in and orbital QPSK/OQPSK yield remains unqualified. Current presets are RS(255,223), TC(128,64), TC(512,256); convolutional channel coding, puncturing, AR4JA and DVB-S2 presets are not implemented (`docs/psk-and-channel-coding.md`, `docs/fec-support.md`). Mission-matched support may recover more IQ telemetry than making a wrong-profile search faster. Those protocol additions are interoperability work, not automatically a new algorithm.
4. **OGG vs IQ boundary**: progressive audio operates on post-FM PCM. Native BPSK/QPSK/OQPSK deliberately requires complex IQ and rejects mono post-FM OGG/WAV. A GPU cannot reconstruct RF carrier phase already discarded by FM demodulation, and compression-side features require the original Vorbis rather than an arbitrary converted WAV.

## Acceptance design for an A40 experiment

Use two separately reported questions: (A) can the identical finite portfolio run faster with identical results, and (B) does extra GPU-enabled search improve unique valid packet yield under a fixed time/energy budget? Report batch size 1, small batches and full-archive batches; warm and cold starts; p50/p95 latency, total throughput, CPU wall/CPU seconds, GPU kernel time, host-device transfer time and peak host/device memory. Measure the exact completed hypothesis count and paired added/lost sets. Preserve CPU controls and negative/noise recordings. Keep future algorithm development separate from the currently running frozen publication comparison.
